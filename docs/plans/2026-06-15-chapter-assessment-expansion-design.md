# 章节小测与章末大测试扩容设计

## 目标

- 每个大章节新增一套视频/PPT 学完后的章节小测：10 道选择、10 道填空、10 道判断、3 道编程，共 33 题。
- 章末大测试按小测体量乘 3：30 道选择、30 道填空、30 道判断、9 道编程，共 99 题。
- 两套卷均整卷作答、一次提交。
- 章末大测试限时 120 分钟；章节小测限时 60 分钟。
- 题目只允许覆盖当前章 KC 与课程证据页；编程题优先按当前章 KC 生成。
- 同一学生同一章的章节小测与章末大测试不得出现重复题目。

## 架构

复用现有 `chapter_test` 整卷引擎，通过 `assessment_kind` 区分 `QUIZ` 与 `FINAL`。两类试卷共用去答案发卷、整卷提交、服务端客观题判分、编程沙箱判题、防作弊计数和结果解析，避免维护第二套考试协议。

章节小测使用 `10/10/10/3` 生成请求。章末大测试使用 `30/30/30/9`，Graph 端拆成 3 个 `10/10/10/3` 批次生成后合并，降低单次结构化输出过长导致的失败概率。

## 数据流

1. 学生在每章最后一个主线小节完成视频与 PPT 后进入 `/chapter-quiz/:chapter`。
2. `prepare` 创建 `assessment_kind=QUIZ` 的记录并异步生成 33 题。
3. 学生开始后获得去答案题面，整卷作答后一次提交。
4. 章末大测试 `prepare` 读取该学生本章最近一套小测题面，提取客观题题干和编程题标题/描述的规范化签名。
5. 签名作为 `excluded_questions` 传入 Graph；Graph 每个生成批次同时排除小测题和前序批次题。
6. 后端在落库前再次校验题型数量、题目签名重复和排除集冲突，校验失败则整次生成失败，不下发不合规试卷。

## 判分

题目内部仍使用整数权重。整卷判分后统一按 `raw_score / raw_max_score` 四舍五入折算为 0–100 分，避免 33 题和 99 题的原始总分破坏既有 60 分通过线、星级公式和教师统计。

逐题结果继续返回原始题目权重与实得权重，方便展示编程题部分通过情况。

## 失败策略

- Graph、证据审查、沙箱自测、题量校验或去重校验失败时保持 `FAILED`，不再用旧的 12 题占位卷冒充新规格。
- 考试期间仍为零 LLM 调用；只有 `prepare` 异步生成。
- `start` 只允许启动 `READY` 记录，未就绪时明确提示稍后重试。
- 旧记录迁移为 `FINAL`，教师统计和星级只统计 `FINAL`，章节小测不参与章末星级。

## 前端

- `ChapterTestPage` 增加 `quiz/test` 模式，复用四类题目组件和统一交卷逻辑。
- 新增 `/chapter-quiz/:chapter` 路由。
- 每章最后一个主线小节在视频与课件均过线后显示“进入章节小测”入口。
- 开考页明确展示题量与时限；提交按钮仍只有整卷交卷，不增加逐题提交。

## 验证

- Backend：两类记录隔离、60/120 分钟、题量请求、最终卷排除签名、0–100 归一化、星级仅看 FINAL。
- Graph：33 题单批生成、99 题三批合并、批次 qid 唯一、排除题拒绝、三审通过。
- Frontend：两条路由、模式化 API URL、题量文案、整卷提交、最终小节入口门槛。
- ECS：注册/登录后分别 prepare/start 两类试卷，核对题型数量、时限、统一提交和题面不重复。
