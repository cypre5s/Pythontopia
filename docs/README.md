# 开发文档索引

按“要求 → 当前规范 → 操作 → 验证 → 历史”的顺序阅读。开发、修复或文档修改的每一轮先复核[已确认要求](requirements.md)，结束时同步记录；最新用户决定优先于已撤销方案和旧验收描述。

## 开始一轮工作

1. 读requirements，确认本轮影响哪些既定要求及是否有新的决定。
2. 按下表选对应规范；只读相关细节，无需每次通读所有文档。
3. 从development执行当前流程；在acceptance确认已有验证和未覆盖边界。
4. 需要追溯原先为什么这样做、失败经过或旧部署时，再读archive。旧记录不是当前操作指令。

## 每份文档只负责一件事

| 文档层级 | 保存什么 | 更新时机 |
| --- | --- | --- |
| requirements | 已确定的要求、稳定编号、细节归属、近期每轮复核 | 每轮必维护；需求改变更新原条目，无新增需求也记录保持结论 |
| product / architecture / api / content / design | 当前行为与规则的主要说明 | 对应行为、字段、脚本或设计变化时原位更新，不追加整轮流水 |
| development | 当前环境、可执行流程、必要配置和排查 | 操作方式变化时更新；不用旧head或机器部署状态冒充通用流程 |
| acceptance | 最新有效矩阵、限制及证据索引 | 验证发生或边界改变时更新；不将未执行写成通过 |
| reborn-migration | 简短接续上下文和剩余事项 | 需要交接、结论变化或待办完成时更新，不复制完整验收 |
| proposals | 尚未确认的评估、方案与基准清单，不构成需求 | 提出提案时新建；一旦确认就并入对应规范并删除过期提案 |
| archive | 当时的全文、失败、跳过、部署过程与出处 | 记录退出现行文档时归档，保留来源提交和原证据 |

[AGENTS.md](../AGENTS.md)是开发约束和入口，细节由上述文档拥有。同一规则保留一个主要说明位置，其余使用链接；发现冲突时核对用户决定与实际实现，不用旧测试或归档反向覆盖要求。

## 每轮维护流程

1. **开始复核**：阅读requirements和相关规范，标明本轮影响编号，识别新要求、替代决定和数据/权限边界。
2. **同步实现与规范**：需求有变化就改对应条目及原因；行为、API、YAML、设计或命令变化同步其拥有文档。没有变化的规范无需机械改写。
3. **如实验证**：代码或内容按影响范围运行检查；纯文档轮检查链接、锚点、归档完整性和事实一致性。结果记录日期、源码/工作区、环境、通过/失败/跳过和未覆盖范围。
4. **维护本轮记录**：每轮都在requirements记录影响范围、需求是否变化、同步文档、核对结果与未执行项；即使没有新增需求，也明确写“要求保持”。不要把所有功能测试计数重复抄入多处。
5. **归档与交接**：旧验收/部署过程进入archive并更新链接；失败和跳过保持原结论，新的成功记录独立保存。续做入口只保留仍适用的上下文和待验证事项。
6. **提交前检查**：运行文档检查，确认没有凭据、SQL或trace进入Git，复核需求与实现一致后用中文提交。

文档检查命令见[开发手册](development.md)。近期需求复核只保留精简窗口，旧记录按[requirements规则](requirements.md#每轮维护流程与完成标准)归档。归档正文可通过[来源清单](archive/2026-11-08-documentation-baseline/manifest.json)核对，不能删失败经过或把失败目录改标成功。

## 来源与使用边界

本机端口、镜像、运行状态和忽略目录的证据只代表相应记录时刻，不保证当前仍可用或其他机器能恢复。实际命令只在开发手册维护，YAML结构示例在内容编写规范维护。

根目录[LICENSE](../LICENSE)、[美术许可](../LICENSE-ART.md)和保留素材来源继续保留。[第三方历史清单](legal/open_source.md)含旧技术栈，当前依赖需结合实际锁文件与上游许可核对，不能据历史清单恢复旧系统。
